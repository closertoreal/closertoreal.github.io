# ТЗ · Эксперимент «Распределение ПСД по шагам СМР»

Статус: рабочая версия / аналитический эксперимент. Ветка `NEW`, отдельная вкладка `new/psd-map/index.html`. Исходные страницы и процесс СМР остаются без редактирования содержимого.

## 1. Цель и проверяемая гипотеза

Обнаружить потенциальные пробелы **схемы процесса** относительно документов из перечней ПСД НКНХ (Приложение 1) и ДГП (Приложение 13.1). Полнота перечней ПСД принимается как внешний исходный артефакт и автоматически здесь не доказывается.

**Непривязанный документ** означает «не найдено подтверждённого соответствия шагу», но сам по себе **не доказывает**, что шаг пропущен. Причины: пробел процесса, слишком укрупнённая детализация, отсутствие применимости, неверный тип документа, особенности площадки, неоднозначность текста.

## 2. Исходные данные и единица анализа

- Исходная единица: **строка конкретного реестра ПСД**, включая площадку, полный путь, код и точное наименование.
- Два реестра не сливаются автоматически, если формально совпадают названия: коды и контексты сохраняются.
- Каталог без документов не считается документом и не распределяется.
- Схема: 35 существующих шагов в актуальном порядке ветки `NEW`.
- Существующая схема не переименовывается, не переписывается и не подменяется новой.

Демонстрационный набор на странице: 40 ранее открыто использованных разновидностей актов из интерфейса ПСД, представлен двумя источниками (80 записей). **Не считать набор полной выборкой ПСД.**

Для полной проверки пользователь загружает *плоский* XLSX/CSV с полями `Путь`, `№ п/п`, `Наименование документа`, `Тип записи`. Поддерживаются оба листа `Приложение 1` и `Приложение 13.1`, либо отдельные файлы.

Полные исходные корпоративные реестры в публичный GitHub не публикуются. Загрузка читается JavaScript на клиенте; результаты и ручные решения хранятся в `localStorage` этого браузера. Для устойчивого архивирования предусмотрен CSV-экспорт матрицы.

## 3. Визуальная модель

Слева: строки документов в виде «кирпичиков», сгруппированных по пути вида работ, с сохранением исходных кодов и источника.

Справа: схема из 35 шагов, сгруппированная по стадиям. В каждом шаге показываются количество распределённых документов и примеры названий. При выборе шага слева остаются только связанные с ним строки.

Кнопка **«Распределить по шагам»** запускает консервативные текстовые правила сопоставления. Первые несколько найденных назначений анимируются для визуального представления; анимация не служит доказательством правильности распределения. При `prefers-reduced-motion` движение не воспроизводится.

## 4. Матрица четырёх функций ИД

У каждой записи четыре независимых признака:

| Код | Что подтверждает |
| --- | --- |
| `done` | Факт выполнения конкретных видов и объёмов работ |
| `quality` | Требуемое качество, соответствие проекту и НТД |
| `them` | Участие конкретных исполнителей |
| `next` | Возможность последующих работ |

Каждый признак имеет три состояния: `?` (не проверен), тег (да), `−` (нет). Пустая / неразмеченная ячейка **не тождественна отрицанию**. По тегам можно фильтровать.

## 5. Трассируемость и статусы

У каждого документа хранится `source + code + path + name`, связь с шагом, основание и статус:

- **Не распределено**: алгоритм ещё не запускался.
- **Предложено**: одно предполагаемое соответствие, не проверено человеком.
- **Несколько шагов**: неоднозначный кандидат.
- **Без шага**: правило не нашло подходящего действия.
- **Подтверждено**: человек явно назначил шаг и подтвердил.
- **Вне рассматриваемого процесса**: отложено/исключено из текущего предмета; может быть возвращено.

Автоназначение не является утверждённой логикой процесса. Обобщённое сопоставление с шагом 18 («Приёмочная инспекция») помечается как **групповая гипотеза**: оно не доказывает, что отдельная операция, предусмотренная ПСД, детализирована в схеме.

## 6. Выявление пробелов

Фильтр «Без шага» и отдельная нижняя панель дают список кандидатов. Экспорт «Вопросы по пробелам» формирует строки для обсуждения с профильными участниками:

«В каком шаге создаётся, оформляется или проверяется документ? Возможно ли, что действие отсутствует в схеме?»

В список вопросов также попадают неоднозначные сопоставления. Перед утверждением нового шага аналитик проверяет применимость документа и фактическую глубину схемы.

## 7. Критерии приёмки

1. При загрузке полного плоского XLSX двух площадок распознаны все строки с типом «Документ»; каталоги без документов исключены. Счётчики должны совпасть с исходными файлами.
2. Номер шага, название и порядок соответствуют схеме `NEW` на момент создания вкладки.
3. Схема СМР и протокол остались доступны на прежних вкладках; данные прежних карточек не изменились.
4. Нераспределённые и неоднозначные строки не скрываются, не выдаются за подтверждённые и экспортируются.
5. Все четыре признака можно изменять независимо и выгружать отдельными столбцами CSV.
6. В браузере поддерживаются поиск, фильтры по площадке и статусу, назначение шагов и явное подтверждение.
7. Данные не публикуются из браузера в GitHub. Для другой машины используется выгрузка матрицы; автоматической синхронизации между устройствами нет.
8. Анимация отключается при настройке уменьшенного движения.

## 8. Границы текущей реализации

- MVP проверяет *текстовую трассируемость документ → шаг*. Он **не моделирует полноценный граф операций и обязательных документов** по каждому отдельному виду работ.
- Критерии нормативной обязательности, условия применимости, а также утверждение новых шагов требуют отдельной экспертной верификации.
- Правила `done/quality/them/next` намеренно **не проставляются автоматически**, поскольку такой вывод требует анализа назначения документа.
- Загрузка XLSX использует внешнюю библиотеку SheetJS через CDN. Без доступа к CDN можно импортировать CSV, экспортированный из Excel.
- Демо соответствует уже использованным актам, **не** всему перечню; для полного анализа необходимо загрузить плоский реестр.

## 9. Следующий аналитический этап (не выполнено автоматически)

После ручной верификации можно формировать отдельную матрицу `вид работ → операция/контроль → документ → функция ИД → нормативное/проектное основание → шаг процесса → статус соответствия`. Только тогда вывод об отсутствии документа/процессного действия станет обоснованным.
