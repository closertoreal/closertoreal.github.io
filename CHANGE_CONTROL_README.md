# Контроль точечных изменений сайта (Change Scope Guard)

**Статус: прототип в PR #1. Не включён на `master`; действующий сайт не изменён.**
Стоимость: **0 ₽** (публичный репозиторий, Python 3, стандартные GitHub Actions и Rulesets).
Цель: автоматическая защита от незапрошенной переработки согласованного текста. [ТЕСТ, НЕ ПУБЛИКОВАТЬ]

## Что проверено в этом репозитории

- Репозиторий: `closertoreal/closertoreal.github.io`, публичный; главная ветка `master`.
- Рабочие материалы СМР находятся также в `NEW`, контент `new/index.html` содержит `MODEL.steps`.
- GitHub Actions успешно запустил тесты валидатора в изолированной ветке.
- Тесты включают реальное содержимое `new/index.html`: изменение только поля `input` шага 17 — PASS; дополнительная правка заголовка в том же HTML — FAIL.
- По результатам проверки репозиторных Rulesets до внедрения: `[]`.
- Разрешение на управление Rulesets отсутствует среди действий подключённого GitHub; настройка Branch Protection API возвращает 403. Это ограничение соединения, не стоимость GitHub.

## Файлы

- `tools/change_scope_guard.py` — проверяет весь Git-дерево относительно base-коммита и точную ожидаемую замену байт.
- `tools/test_change_scope_guard.py` — изолированные сценарии допустимых и недопустимых замен.
- `tools/test_real_site_scope_guard.py` — тесты на **реальном** `new/index.html`, но только в временном Git-каталоге теста.
- `.github/workflows/change-scope-tests.yml` — запускает тесты только в прототипной ветке (не публикация).
- `.github/workflows/change-scope-guard.yml` — предполагаемая независимая PR-проверка по спецификации, фиксированной в доверенном base-коммите.

## Как выглядит согласование без ручного изучения diff

Для нового изменения:

1. **Ты** формулируешь правку в чате: «Измени конкретный текст шага 17, всё остальное не меняй».
2. **ИИ** определяет точные `old`, `new`, файл и идентификатор правки, показывает предлагаемое изменение. Изменения сайта на этой стадии не допускаются.
3. **После твоего согласования** спецификация сохраняется отдельным коммитом **в доверенном `master`**, например `.change-control/approvals/step17-input-20261123.json`.
4. **ИИ** создаёт ветку `approved/step17-input-20261123` **от уже обновлённого `master`** и выполняет только указанную замену.
5. **ИИ** создаёт PR. GitHub Actions исполняет проверяющий код и читает спецификацию **из base-коммита**, а не из PR. Любая посторонняя правка, даже в том же HTML, даёт `FAIL`.
6. Слияние разрешается **только при успешной required status check** в Ruleset; сайт публикуется по текущему процессу публикации основной ветки.

Формат уже согласованной спецификации:

```json
{
  "replacements": [
    {
      "path": "new/index.html",
      "old": "предъявленная ИД",
      "new": "ИД на объём СМР"
    }
  ]
}
```

`old` должен встретиться **ровно один раз**: при повторяющихся фразах ИИ обязан включить достаточный контекст (например, весь текст свойства `MODEL.steps`) и не угадывать целевой шаг. Для нескольких замен разрешено несколько записей.

Идентификатор `step17-input-20261123` здесь только иллюстративный: перед фактическим изменением он назначается уникальным. Ветви допускаются формата `approved/[a-z][a-z0-9-]{2,63}`. Для других ветвей проверка всегда `FAIL`. Fork PR пока не поддерживаются.

**Почему спецификация не находится в PR?** Потому что ИИ мог бы отредактировать её вместе с исходными данными, разрешив себе незапрошенные изменения. Внесённые только в PR подтверждения никогда не считаются согласованными.

## От чего защищает

- Изменение неразрешённых строк того же файла.
- Изменение любых других файлов (включая удаление, добавление, перемещение и атрибуты Git).
- Изменение проверяющего скрипта, Actions workflow или спецификации в кандидатном PR.
- Пропуск утверждённой замены или неоднозначность исходного фрагмента.

**Чего не гарантирует:** правильность утверждённого пользователем содержимого; настоящую человеческую авторизацию, если модель имеет доступ писать и в доверенный `master`; невозможность обхода правил администратором репозитория. Требуется отдельное ограничение прав ИИ или иной независимый канал подтверждения.

## Дальнейшая настройка GitHub (однократно)

Только после проверок CI и подтверждения схемы доверенного согласования:

1. Перенести скрипт, тесты и production workflow в default `master` (без изменений содержимого сайта).
2. Убедиться, что Actions допускает событие `pull_request_target`. По текущей документации GitHub для публичных репозиториев событие может быть заблокировано политикой выполнения; нужно разрешить его в настройках Actions. Workflow исполняет код только из доверенного `master` и никогда не исполняет содержимое PR.
3. В `Settings → Rules → Rulesets` создать активный branch ruleset для `master`: `Require a pull request before merging`, `Require status checks to pass`, статус `exact-change-check`. Не добавлять обходы; указать ожидаемый источник GitHub Actions, если доступен.
4. Убедиться, что админ/ИИ не могут обходить или отключать настройки; при необходимости ограничить разрешения установленного GitHub-коннектора или перенести проверки в независимый контур.
5. Прогнать один тестовый PR по правилу выше. Никаких новых платных услуг не подключать.

**Почему GitHub Actions не достаточно сам по себе:** без Ruleset прямой коммит в `master` продолжит проходить в обход CI. ИИ не может подтвердить подключение Ruleset текстовым отчётом; состояние нужно проверить средствами GitHub.

### Команда для автономного прогона тестов

```bash
python3 -m unittest discover -s tools -p 'test_*scope_guard.py' -v
```

Система рассчитана на использование ИИ без ручного чтения Git diff, но первичное включение административных правил GitHub может потребовать один раз открыть Settings: доступный коннектор не имеет действия записи Ruleset. GitHub Enterprise и платные сторонние сервисы не требуются.
