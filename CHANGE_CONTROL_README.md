# Change Scope Guard (прототип, не включён на сайте)

Цель: гарантировать **побайтовую неизменность всех отслеживаемых Git-файлов, кроме явно разрешённых точечных замен**. Не полагаться на текстовый отчёт ИИ о том, что «ничего лишнего не изменено».

## Что проверено при исследовании

- Сайт: \`closertoreal/closertoreal.github.io\`, публичный репозиторий, основная ветка \`master\`.
- Есть дополнительная ветка \`NEW\`.
- Процессные данные находятся в том числе в \`new/index.html\`: \`MODEL.steps\` (массив объектов с \`code\`, \`title\`, \`input\`, \`action\`, \`output\`).
- В основной ветке на момент аудита нет \`.github/workflows/\`; репозиторные Rulesets не обнаружены.
- GitHub Connector способен делать коммиты и сообщает \`admin: true\`. Настройка Rulesets через доступные действия коннектора недоступна; ответ Branch Protection API был \`403\`.

## Состав прототипа

- \`tools/change_scope_guard.py\`: независимое сравнение Git-деревьев и точного ожидаемого содержимого файлов.
- \`tools/test_change_scope_guard.py\`: позитивные и негативные тесты.
- \`.github/workflows/change-scope-guard.yml\`: проверка PR. Она исполняет только скрипт из **доверенного base-коммита**; исходники PR используются только как данные.

**Внимание:** этот workflow пока в тестовой ветке и НЕ защищает \`master\`. Не следует сливать прототип как готовую защиту без проверки и настройки правила обязательного статуса.

## Модель точных правок

\`.change-control/approvals/pr-NNN.json\`, пример:

\`\`\`json
{
  "replacements": [
    {
      "path": "new/index.html",
      "old": "предъявленная ИД",
      "new": "ИД на объём СМР"
    }
  ]
}
\`\`\`

Фрагмент \`old\` обязан встречаться **ровно один раз**. При необходимости указывают более длинный контекст или всю строку/свойство, чтобы замена была однозначной. Скрипт вычисляет ожидаемый текст файла из доверенного base-коммита, применяет утверждённые замены и сравнивает байты с кандидатом. Любая дополнительная правка в этом же файле, другом файле, изменение режима файла, добавление или удаление файла вызывает \`FAIL\`.

### Важное архитектурное ограничение

Спецификация разрешённых правок должна быть уже зафиксирована в **доверенной base-ветке** на момент проверки PR. Файл спецификации внутри самой ветки PR не считается подтверждением: ИИ мог бы изменить его вместе с кодом. Для каждого PR с новыми разрешёнными правками требуется отдельный шаг фиксации утверждённой спецификации в доверенном источнике. Без независимого подтверждения разрешённого изменения невозможно программно доказать, что его согласовал пользователь.

## Тесты

Локально в корне репозитория (Python 3, Git):

\`\`\`bash
python3 -m unittest discover -s tools -p 'test_change_scope_guard.py' -v
\`\`\`

Проверяются успешная точная замена и отказ для: посторонней строки в том же файле, другого файла, добавленного/удалённого файла, пропущенной правки, неоднозначной замены, попытки разрешить изменение самого workflow и добавления спецификации в PR.

## Для последующего ввода в эксплуатацию

1. Проверить тесты и провести пробу в отдельной ветке.
2. Согласовать один минимальный пример правки и сохранить его JSON-спецификацию **в доверенном источнике**, а не через коммит ИИ в PR.
3. Перенести validator + workflow в \`master\` без изменения текстов сайта.
4. Настроить \`Settings → Rules → Rulesets\`: PR обязателен, status check \`exact-change-check\` обязателен, обход запретить.
5. Изолировать права ИИ от настроек защиты/базовой ветки. **Пока коннектор имеет admin-права, гарантированной неотключаемой защиты нет**. Нужен отдельный токен/роль с ограниченными разрешениями или иной независимый контур.
6. При публикации через GitHub Pages проверить, что деплой следует только за принятыми изменениями доверенной ветки.

Если правила доступа не позволяют выполнить пункты 4–5, считать систему **аудитором изменений**, а не техническим запретом.

## Что НЕ входит

- Автоматическая семантическая оценка согласованности текста или полноценная архитектура модели.
- Защита от администратора репозитория или злоумышленника с доступом к настройкам.
- Автоматическая публикация.
- Платные тарифы GitHub Enterprise, сторонние CI/CD и платные API.

Используются штатные бесплатные возможности публичного репозитория GitHub и стандартный Python.
